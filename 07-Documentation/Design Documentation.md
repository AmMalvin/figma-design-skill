# Design documentation

Owns artifact explanation and traceability. Document what another contributor needs to implement, critique or reuse the work; do not require a full library manual for a local edit.

For substantial work include task/context, scope, evidence/assumptions, information/interaction decisions, alternatives and trade-offs, system reuse, relevant states, adaptive behavior and validation limits. Link current sources rather than copying their guidance.

For a shared component use [Component Contract](../Templates/Component%20Contract.md); for a feature use [Design Brief](../Templates/Design%20Brief.md) and [Design Decision](../Templates/Design%20Decision.md) when useful. Examples expose meaningful constraints, not only an attractive default state.

Separate facts, intended behavior, inspected artifact and observed tests. Keep node/component/token/code references stable and identify superseded guidance. Record unsupported capabilities and unresolved business rules with their impact.

Anatomy/screens belong with their behavior contract. Research evidence belongs with its source. Product-specific decisions should not become universal system rules. New module structure follows [Module Blueprint](../Templates/Module%20Blueprint.md).

Deliverables may be inline or repository artifacts according to user scope; no requirement to create documentation folders in another project.
