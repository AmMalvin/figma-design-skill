# Reference evaluation

Evaluate fitness, not prestige. Follow [source precedence](../00-Core/AI%20Operating%20Rules.md).

| Question | Evidence to record |
| --- | --- |
| Same task and decision risk? | User, goal, reversibility and information priorities |
| Same operating context? | Platform, input, device, density, network, locale and expertise |
| Complete interaction inspected? | Entry, action, feedback, recovery and return; separate screenshots from observed behavior |
| Existing system compatible? | Components and semantic roles that can express the principle |
| Accessible and feasible? | Applicable standards, implementation dependencies and unknowns |
| What is distinctive and useful? | Composition or behavior solving the task, rather than copied decoration |
| What conflicts? | Branding, tokens, controls, content, assumptions or accessibility failures |
| When would it fail? | Conditions requiring a different model and a concrete alternative |

Record fit as applicable, adaptable, unsuitable or unknown, with a reason. Do not average away a critical accessibility or safety conflict. An award is a discovery signal; a shipped pattern is observational evidence, not proof of task success. A design-system document explains that system's contract, not a mandate to import its values.

For comparison, use the same task and inspect at least the paths necessary to resolve the decision. More sources are useful only if they change confidence or expose a trade-off. Keep competitor facts separate from proposed opportunities. State an inference explicitly.

Review date means content inspected on that date. Checked date means access attempted. Uninspected entries may have a checked date and proposed study questions, but no extracted principles or invented review date. Revisit sources before relying on unstable details.
